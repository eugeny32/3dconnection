# HID-протокол: 3Dconnexion SpaceMouse Pro

> Снято по факту с реального устройства (Фаза 0 дорожной карты, `docs/PLAN.md` §5).
> Сырые дампы — в `tests/fixtures/spacemouse_pro_*.jsonl`, формат записи:
> `{"t": <секунды от начала захвата>, "report_id": <int>, "data": [<байты после report_id>]}`.

## Устройство

| Поле | Значение |
|---|---|
| Manufacturer | `3Dconnexion` |
| Product | `SpaceMouse Pro` |
| Vendor ID | `0x046D` |
| Product ID | `0xC62B` |
| Usage Page | `1` (Generic Desktop) |
| Usage | `8` (Multi-axis Controller) |

VID/PID вынесены в `spacemouse_bridge/device_ids.toml`, в коде не хардкодятся
(см. `CLAUDE.md`).

## Конфликт с драйвером

Пока запущен официальный 3DxWare (процессы `3DxService.exe`, `3dxnlserver.exe`,
`3dxpiemenus.exe`, `3DxProfileServer.exe`, `3DxVirtualLCD.exe`, служба
`Mgl3DCtlrRPCService` — «3Dconnexion Broker Service»), прямое чтение через
`hid.Device(vid, pid).read()` не получает вообще ничего: 0 репортов даже при
активном движении шариком. Держит устройство именно процесс `3DxService.exe`
(обычный процесс пользовательской сессии, не служба SCM) — после его
завершения (`Stop-Process`) чтение сразу начинает работать. Служба
`Mgl3DCtlrRPCService` — отдельная, останавливается только с правами
администратора и на захват репортов не влияет напрямую.

## Формат репортов

Устройство относится к «старому поколению» по классификации `docs/PLAN.md`
§3.1: три report ID, а не один общий. `hid.Device.read()` возвращает первым
байтом report ID, дальше — тело репорта.

| Report ID | Длина тела (байт) | Содержимое |
|---|---|---|
| `0x01` | 6 | Tx, Ty, Tz — по `int16 LE` на ось (перемещение) |
| `0x02` | 6 | Rx, Ry, Rz — по `int16 LE` на ось (вращение) |
| `0x03` | 6 | Битовая маска кнопок, `uint48 LE` (побайтовое накопление) |

Оси **не** приходят одним репортом — перемещение и вращение это два разных
сообщения, отправляемых почти одновременно (разница в таймстемпе `t`
в дампах — единицы миллисекунд), но раздельно. Совмещение в единое состояние
6DoF — задача `core/state.py` (§6.2 задача 4), а не декодера.

В покое (шарик не тронут) устройство **не шлёт вообще никаких репортов** —
не только report 1/2 уходят в тишину, нет и «нулевого» heartbeat-репорта.
Значит нормализатору нельзя полагаться на входящий поток для детекта
отпускания — нужен собственный таймаут (например: нет репорта N мс → считать
ось нулевой), это учтено в `core/filters.py`/`core/state.py`.

## Диапазон осей

Замерено по чистому отклонению одной оси до упора (без нажима до
физического стопора, просто до предела хода):

| Ось | Диапазон при захвате | Остальные оси (шум/паразитная связь) |
|---|---|---|
| Tx | −328…350 | ty ±~100, tz 0…184, rx 0…19, ry ±~99, rz ±~77 |
| Ty | −350…350 | tx −128…6, tz 0…158, rx −88…24, ry −124…11, rz ±~45 |
| Tz | −350…350 | tx −120…42, ty −111…249, rx −88…145, ry −65…124, rz −12…67 |
| Rx | −350…350 | tx −1…70, ty −114…153, tz −48…25, ry −106…80, rz −119…28 |
| Ry | −350…350 | tx −62…77, ty −54…71, tz −26…65, rx −28…99, rz −23…80 |
| Rz | −350…350 | tx −11…23, ty −23…119, tz 0…70, rx −19…78, ry −32…26 |

Практический диапазон — **±350**, совпадает с верхней границей из
`docs/PLAN.md` §3.1 (±350 или ±512 в зависимости от прошивки). Значимая
паразитная связь между осями (десятки единиц из ±350, т.е. ~10-30%)
подтверждает необходимость deadzone и dominant-axis подавления из §3.3 —
без них, например, чистый толчок по Tx всегда чуть «утекает» в rz/ry.

## Кнопки

Report `0x03`, тело 6 байт, читается как `int.from_bytes(data, "little")`.
Нажатие и отпускание — отдельные репорты (repeat не происходит, пока кнопка
удерживается): нажатие даёт ненулевую маску, следующий репорт при отпускании
— `000000` (все нули). Наблюдались независимые биты в разных байтах
(например `01 00 00 00 00 00`, `00 00 80 00 00 00`, `00 00 00 01 00 00`,
`00 00 00 02 00 00`, `00 00 00 04 00 00`, `00 40 00 00 00 00` и т.д.) —
соответствует россыпи из ~15 физических кнопок SpaceMouse Pro, конкретное
сопоставление бит → надпись на корпусе не снималось (не критично для MVP,
можно достать позже через `--dump` и сверку вручную).

## Фикстуры

`tests/fixtures/`:

* `spacemouse_pro_axis_tx.jsonl`, `..._ty.jsonl`, `..._tz.jsonl` — чистое
  перемещение по одной оси (пользователь двигал строго по одной оси).
* `spacemouse_pro_axis_rx.jsonl`, `..._ry.jsonl`, `..._rz.jsonl` — чистое
  вращение по одной оси.
* `spacemouse_pro_buttons.jsonl` — последовательность нажатий/отпусканий
  разных кнопок.

Идейно это покрывает требование §6.3 плана («покой, чистое вращение по одной
оси, смешанный жест») с запасом — по одной чистой фикстуре на каждую из 6
осей вместо одной; «смешанный жест» тестами пока не покрыт отдельным файлом,
его несложно получить, играя в `ReplayReader` любой из чистых фикстур на
фоне другой (пока не критично для decoder-тестов, которые проверяют разбор
одного репорта за раз).
